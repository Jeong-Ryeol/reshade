# Sherbet 스프레이 트레이너 설계

작성일 2026-07-30 · 대상 브랜치 `sherbet-base` · 목표 릴리스 **1.2.0**

PVP 유저가 자기 반동 보정 패턴을 기록·확인할 수 있게 한다.
게임 메모리를 읽지 않고 **입력만 관찰**하므로 안티치트·평판 위험이 없다.

---

## 0. 배경과 포지셔닝

Sherbet 구매자는 **인게임 사진가**와 **PVP 유저**로 나뉘고, PVP 쪽이 더 많다.
기존 상품은 전부 "화면 색을 바꾸는" 축(프리셋·fx)이었다. 이 기능은 **촬영/훈련 워크플로**라는
새 축이며, 프리셋과 달리 복사가 쉽지 않다.

**시장 조사 결과(2026-07-30):** FiveM 생태계에는 반동을 *바꾸는* 서버 측 스크립트만 있고
(Real Weapon Recoil, CFX-wepRecoil 등) 훈련·시각화 도구는 없다. 훈련 도구는 CS2/발로란트
쪽에만 있으며 전부 **게임 밖 웹 도구**다.

**FiveM 서버마다 반동 스크립트가 달라 패턴이 제각각**이므로, CS2 트레이너처럼 정답 패턴을
미리 박아넣는 방식은 성립하지 않는다. **직접 쏘면서 기록하는 방식**만이 그 서버·그 무기에
자동으로 맞춰진다. 파편화가 오히려 이 접근에 유리하다.

---

## 1. 무엇을 기록하는가 — 그리고 무엇을 기록하지 **않는가**

| | 가능 | 근거 |
|---|---|---|
| 총알이 실제로 박힌 위치 | ❌ | 게임 메모리에만 존재. 읽으면 안티치트 영역 |
| 무기·반동 수치 | ❌ | 동상 |
| 화면 픽셀 | (안 씀) | 이 기능은 화면을 읽지 않는다 |
| **발사 시점** | ✅ | `_input->is_mouse_button_down(0)` 상승 엣지 |
| **마우스 이동량** | ✅ (§3 전제) | raw input `lLastX/lLastY` |

기록하는 것은 **"총알이 어디 갔나"가 아니라 "내 손이 어떻게 움직였나"**다.
프로가 훈련하는 것이 정확히 후자이고, 원인을 보여주므로 결과보다 교정에 직접적이다.

---

## 2. 핵심 규칙 — 분류하지 않는다

클릭할 때마다 점을 하나 찍고, **무발사 간격으로만 구간을 나눈다.**

```
클릭 → 현재 누적 오프셋을 점으로 기록
마지막 발사 후 400ms 경과 → 구간 종료, 다음 클릭은 새 구간(오프셋 0,0)
```

사격 방식을 판별하는 로직은 **없다.** 같은 코드에서 모양이 저절로 갈린다:

| 방식 | 결과 모양 |
|---|---|
| 탭 (한 발씩) | 구간당 점 1개 → 산점도 |
| 버스트 (2~3발) | 짧은 궤적 여러 개 |
| 연발 | 구간당 점 20~30개 → 긴 궤적 |

**왜 분류하지 않는가:** 임계값 판별은 실전에서 오분류가 잦다(급한 탭 두 번 → 버스트로,
렉 → 연발이 쪼개짐). 오분류된 데이터는 엉뚱한 칸에 들어가 통계를 오염시킨다.
도구는 사실만 기록하고 해석은 사용자가 한다.

## 3. ⚠️ 전제와 그 검증 — 구현 맨 앞에서 확인할 것

리쉐이드의 raw input 처리(`source/input_windows.cpp:173~212`)는 마우스 **버튼과 휠은**
읽지만 **이동량 `lLastX`/`lLastY`는 읽고 버린다.** 커서 위치(`_mouse_position`)는 게임이
마우스를 캡처하면 움직이지 않으므로 쓸 수 없다.

또한 `input_windows.cpp:184`가 이렇게 되어 있다:
```cpp
if (raw_input_window == s_raw_input_windows.end() || (raw_input_window->second & 0x2) == 0)
    break;  // 레거시 마우스 메시지가 켜져 있으면 여기서 처리하지 않음
```
**게임이 raw input 을 등록하지 않으면 이 경로 자체가 돌지 않는다.**

### 검증 절차 (구현 첫 작업)

1. `input_windows.cpp` 에 `lLastX/lLastY` 누적 두 줄을 넣고 빌드
2. 게임에서 마우스를 흔들며 디버그 표시로 숫자가 증가하는지 확인
3. 증가하지 않으면 §5(궤적) 전체를 접고 §4(발사 기록)만 진행

**궤적 관련 작업이 전체의 약 70%다.** 이 확인은 5분이면 되고, 뒤로 미루면 그 70%가
통째로 버려질 수 있다.

### 2층 구조 — 전제가 깨져도 기능이 죽지 않게

| 층 | 필요한 것 | 전제 깨지면 |
|---|---|---|
| **발사 기록** — 발수·연사간격·RPM·구간 나누기 | 버튼(이미 동작) | 그대로 동작 |
| **궤적** — 보정 경로, 실시간 표시, 겹쳐보기 | 이동량 | 이 부분만 비활성, "이 게임에서는 마우스 이동을 읽을 수 없어요" 표시 |

## 4. 아키텍처

```
[입력]  input_windows.cpp  raw lLastX/lLastY 누적
          ↓
        input.hpp  raw_mouse_delta_x/y() (읽고 리셋) · raw_mouse_available()
          ↓
[순수]  sherbet_spray.hpp  recorder — 누적·구간나누기·링버퍼   ← 맥 호스트 테스트
          ↓
[표시]  runtime_gui.cpp
          ├ 오버레이 게이트 바깥: 매 프레임 on_frame() + 실시간 궤적(토글 ①)
          └ 에임 탭 안: 차트·통계·겹쳐보기(토글 ②)
```

**판정 로직을 순수 층에 몰아넣는 이유는 1단계(자동 업데이트)와 같다** — 맥에서 실제로
단위테스트할 수 있는 것은 그 층뿐이고, Windows 의존 코드는 CI 컴파일이 유일한 검증이다.

### 데이터 모델 (`source/sherbet_spray.hpp`, 순수 C++17)

```cpp
namespace sherbet { namespace spray {

struct shot    { float x, y;  float t; };  // 구간 시작 기준 누적 오프셋(raw), 구간 시작 이후 경과 초
struct segment { std::vector<shot> shots; };

class recorder
{
public:
    // dt = 프레임 간격(초), dx/dy = 이번 프레임 raw 이동 누적, fire = 좌클릭 상승 엣지
    void on_frame(float dt, int dx, int dy, bool fire);
    const segment *current() const;                 // 진행 중 구간(없으면 nullptr)
    const std::vector<segment> &history() const;    // 완료된 구간, 최신이 뒤. 최대 kMaxSegments
    void clear();
    void set_gap_ms(int ms);                        // 기본 400
private:
    // 누적 오프셋, 마지막 발사 이후 경과, 링버퍼
};

constexpr std::size_t kMaxSegments = 20;
}}
```

**세션 한정 — 파일을 만들지 않는다.** 게임을 끄면 사라진다. 스프레이 훈련은 한 자리에서
몇 분간 반복하는 형태라 최근 몇 구간이면 충분하고, 날짜 비교는 같은 무기·거리·서버여야
의미가 있어 관리 비용 대비 가치가 낮다. 요청이 생기면 그때 얹는다(배포가 싸졌으므로).

## 5. 화면 표시

### 5.1 실시간 궤적 (토글 ①, 기본 꺼짐)

`ImGui::GetForegroundDrawList()` 로 그린다 — 커스텀 조준점(`runtime_gui.cpp:1181`)과 같은 방식이며,
**오버레이 게이트(`if (_show_overlay)`, 1512행) 바깥**이라 오버레이를 열지 않아도 그려진다.

- 화면 중앙 기준, 현재 구간의 점을 선으로 잇는다
- 마지막 발사 후 2초에 걸쳐 페이드아웃
- **배율 슬라이더 필수** — raw 단위는 사람마다 감도가 달라 픽셀로 바꾸는 계수가 필요하다

### 5.2 차트 (토글 ②, 기본 꺼짐)

에임 탭 안:
- 격자 배경 + 구간 목록(발수 · 평균 연사간격 · 시각)
- **최근 5개 겹쳐보기** 체크박스 — 일관성이 눈에 보이는 핵심 기능
- 통계: 발수, 평균 RPM, **종료 지점 편차**

**종료 지점 편차의 정의:** 최근 N개 구간의 **마지막 점 좌표**를 모아 그 중심(평균)을 구하고,
각 점이 중심에서 떨어진 거리의 평균을 낸다(단위: 화면 픽셀, 배율 적용 후).
값이 작을수록 매번 같은 자리에서 스프레이가 끝난다는 뜻이고, 그것이 일관성이다.
구간이 2개 미만이면 표시하지 않는다. 점이 1개뿐인 구간(탭)도 그 점이 곧 마지막 점이므로 포함된다.

### 5.3 기록을 멈추는 조건

**오버레이가 열려 있으면 기록하지 않는다.** UI 를 조작하는 마우스 움직임이 궤적으로
들어가면 데이터가 오염된다.

## 7. 설정 (config 저장)

```
[OVERLAY]
SherbetSprayLive   = 0     화면 실시간 궤적
SherbetSprayChart  = 0     차트 표시
SherbetSprayScale  = 1.0   raw → 픽셀 배율
```

두 토글은 **독립**이다. 둘 다 끄거나, 하나만 켜거나, 둘 다 켤 수 있다. **기본은 둘 다 꺼짐.**

## 10. 안전 · 평판

- 게임 메모리 읽기 ❌ · 화면 픽셀 읽기 ❌ · **입력 관찰만** ⭕
- 입력을 **주입하지 않는다** — 매크로가 아니다. 리쉐이드가 이미 후킹 중인 메시지를 읽을 뿐이며,
  후킹 표면이 늘어나지 않는다
- 시야 이점을 만들지 않는다 — 자기 손동작을 보여줄 뿐이다
- 기본값 둘 다 꺼짐

이 성질들 덕에 **"샤벳은 치트가 아니라 훈련 도구"** 라는 포지션을 잡을 수 있다.

## 12. 화면 이동 추정 실험 결과 (2026-07-30, 중단)

`반동 = 화면 이동 − 마우스 이동` 으로 게임의 실제 반동을 뽑아내려 했다. 1D 프로파일 매칭으로
화면 이동을 재는 스파이크를 만들어 실물에서 확인한 결과:

| 조건 | 결과 |
|---|---|
| 정지 상태 | dy −0.04(양호) / **dx +2.19(0이어야 함)** / **신뢰도 X 25%, Y 8%** |
| 마우스를 크게 휘두름 | dx 크게 튐, 신뢰도 상승 — **측정기 자체는 정상 동작** |

**결론: 측정기는 동작하나 반동 크기(발당 수 픽셀)의 신호가 노이즈에 묻힌다.**
세로 신뢰도 8% 는 하필 반동의 주축이다. 원인은 1인칭에서 **화면 중앙을 총기 모델이 가리고**,
그 모델은 카메라에 붙어 있어 화면이 밀려도 함께 밀리지 않기 때문으로 추정된다
(세로 프로파일이 밋밋해져 최적 지점이 구분되지 않는다).

**개선 여지는 있었다** — 중앙 크롭 대신 가장자리 띠(총이 가리지 않는 영역)를 보면 신호가
살아날 가능성이 있고 전송량도 4배 준다. 그러나 **더 나은 대안이 나와서 중단했다.**

### 대안: 잘 쏘는 사람의 궤적을 기준으로 삼는다

게임의 반동을 역산할 필요 없이, **실전에서 맞히고 있는 사람의 보정 궤적**을 정답으로 쓴다.

- 무작위 반동 서버에서도 유효하다 — 그 사람은 어쨌든 맞히고 있다
- 구현 위험이 낮다(코드 내보내기/가져오기 + 고스트 선 + 일치도 %)
- **"프로 궤적" 상품화가 가능하다** — 프리셋과 달리 복사가 쉽지 않다

스파이크 코드(`source/sherbet_motion.hpp`, 에임 탭 진단)는 **기본 꺼짐으로 남겨둔다.**
켜지 않으면 렌더 경로가 이전과 동일하고, 나중에 가장자리 띠로 재시도할 때 기반이 된다.
